# 内核 602/603 系统调用主体实现说明

对应代码：[os/src/syscall/security.rs](../os/src/syscall/security.rs)。
契约来源：[AUDIT_ABI_V1.md](AUDIT_ABI_V1.md)。

最初实现两个内核函数，并通过 `os/src/syscall/mod.rs` 的模块声明参与编译。
2026-09-05 已完成 602/603 的 `match` 分发和用户库封装，用户程序可以通过 `ecall`
调用它们。[auditctl](AUDITCTL.md) 及其 QEMU 测试已验证完整调用路径。
下文主体设计保持不变，原有主机测试直接调用这两个真实函数。

## 1. 主体在 rCore 中的位置

一次系统调用由用户程序把编号放入 `a7`，三个参数放入 `a0`、`a1`、`a2`，
再执行 `ecall`。内核 `trap_handler` 在 `UserEnvCall` 分支读取这些寄存器，
交给 `syscall(id, args)` 分发，最后把函数返回值写回 `a0`。

本次实现的是分发之后的业务处理函数：

| 编号 | 内核函数 | 参数 | 成功返回 |
| ---: | --- | --- | --- |
| 602 | `sys_audit_read` | 输出记录地址、记录容量、已读序号 | 实际复制的记录数，0～32 |
| 603 | `sys_ipc_stat` | 输出统计地址、缓冲区字节数、标志 | 0 |

两者都是读取审计数据的接口。它们不会替 A/C 执行信号授权、管道操作或资源预留。
未来信号/管道系统调用通过安全门面写入事件，这两个调用负责把已经保存的事件和统计
提供给有权限的读取者。

## 2. 读取身份为什么要单独一个函数

`caller_context()` 返回 `(IpcSubject, token)`：

- `IpcSubject` 是当前任务的 PID、UID、Capability 的值拷贝，用于权限判断和失败记录；
- `token` 是当前任务页表的标识，用户地址复制必须依据调用者的地址空间解释指针。

身份从当前任务的 `inner.security.credentials` 取得，不能信任用户传入的 UID。
这里使用已经预留的公共凭据字段，不依赖 A 的 UID 分配器或凭据管理接口。

`inner_exclusive_access()` 返回 `RefMut`。函数结束时局部 `inner` 被销毁，任务借用释放；
返回的结构不含任何 `RefMut` 或任务内部引用。之后审计和用户复制均只使用普通值。
代码中的 `expect` 检查“系统调用一定存在当前任务”的内核调度不变量，不用于解析用户指针。

## 3. 权限与错误处理顺序

`check_permission()` 使用冻结 ABI 的条件：

```rust
subject.uid == 0 || subject.capabilities.contains(CapabilitySet::AUDIT_READ)
```

UID 0 不要求同时拥有能力位；非 root 需要 `AUDIT_READ`，只有 `KILL` 或 `IPC_ADMIN`
不能获得读取权限。该判断也不依赖目前尚未加固的 `policy::authorize` 占位函数。

检查顺序固定为：

```text
身份 → 权限 → 参数 → 输出范围 → 用户内存复制
```

602 在检查实际输出范围前还需要获取快照，以确定本次真正要写多少条。
无权限的调用者在这一步之前已经返回；即使传零容量或非法参数，也先返回 `-EPERM`。
授权后的零容量 602 则返回 0，不生成快照、不访问输出地址。

`finish_control_call()` 汇总所有正常业务出口：

| 情况 | 内核内部结果 | 系统调用返回 | 失败记录的 errno |
| --- | --- | ---: | ---: |
| 无权限 | `PermissionDenied` | -1 | 1 |
| 非法参数 | `InvalidArgument` | -22 | 22 |
| 空输出、范围溢出或复制失败 | `InvalidAddress` | -14 | 14 |

辅助函数使用 `?` 传播错误，最后才调用一次 `record_control_failure`。
因此同一次失败不会在各层重复记账。失败审计保存原始请求的记录数量；统计查询的请求数量
固定为 0，记录中的 `result_value` 也固定为 0。

## 4. 602：游标、快照与逐条复制

`sys_audit_read()` 取得调用者信息，再由 `read_records()` 完成读取。

1. 检查权限，零容量直接返回 0。
2. 调用 `audit::snapshot(after_sequence, capacity)`。
3. 快照内部把单批上限截断为 32，并返回 `sequence > after_sequence` 的记录。
4. 快照为空时返回 0，不检查或访问无须写入的输出地址。
5. 检查实际输出范围，逐条生成 ABI 副本并调用 `copy_to_user`。
6. 全部复制成功后返回 `batch.len`。

`after_sequence` 表示“我已经处理到哪一条”。例如当前保留 101～140，调用者传入 110：
本次返回 111～140，共 30 条；下次传 140，若没有新事件就返回 0。
传 `u64::MAX` 也返回空结果，由已有快照算法避免游标加法溢出。

如果调用者期望的下一条早于最旧保留序号，已有快照算法设置 `gap_before`。
`batch.record_at(index)` 只给第一个 ABI 副本附加 `GAP_BEFORE`，不回写内部事件。

快照是固定容量的值拷贝，函数返回时已经释放审计借用。即使复制第一条之后产生新事件，
本次仍返回原有快照；新事件留给下一次游标读取。代码逐条构造 80 字节的 ABI 记录，
避免额外在仅 8 KiB 的内核栈上放置一个 32 × 80 字节的输出数组。

## 5. 为什么不用裸指针偏移

用户传来的指针只是用户虚拟地址；它不能当作当前内核可直接解引用的 Rust 指针。
主体仅把它作为整数计算目标地址，然后交给 `copy_to_user(token, destination, &record)`。

`check_output_range()` 使用：

```text
bytes = count.checked_mul(item_size)
end   = start.checked_add(bytes)
```

实际要写数据时，地址 0 被拒绝；乘法或加法无法表示时返回 `InvalidAddress`。
602 的 `count` 是实际快照数量，不是未经限制的用户容量，所以 `capacity = usize::MAX`
仍然最多复制 32 条，不会产生巨额分配或扫描。

后续 `start + index * 80` 位于已经校验的区间内，不会整数回绕。
这里不对用户地址创建切片，也不使用假定同一内存对象的裸指针 `.add()`。

这一层只能检查空地址和算术溢出。地址是否属于用户页、是否可写、是否跨页或未对齐，
仍须由 B 的统一复制接口处理。当前 `mm/user_access.rs` 直接调用 `translated_refmut`，
尚不具备最终安全语义，不能据此宣称所有非法地址都安全返回 `EFAULT`。

## 6. 复制失败后如何重试

假设本次快照为 11、12、13，前两条成功，第三条的 `copy_to_user` 返回错误：

- 主体返回 `-EFAULT`，不会把“已经写了 2 条”当成成功结果；
- 用户缓冲区可能已经包含前缀数据；
- 环形缓冲区没有消费或删除这些记录；
- 统一出口追加一次 602 失败事件；
- 调用者保留原游标 10，修复输出缓冲区后重新读取。

“非破坏性”表示读取本身不删除事件，不等于旧日志无限保留。持续追加以及失败记录自身
仍可能触发正常的环形覆盖；重试时应继续检查 `GAP_BEFORE`。

## 7. 603：一致的统计与精确写入长度

`read_stats()` 先检查权限，再检查 `flags == 0` 和 `out_size >= 80`。
如果参数无效，即使指针也无效，仍返回 `-EINVAL`，不会调用用户复制。

输出范围只检查实际要写的 80 字节。随后：

```rust
let record = audit::stats().to_record();
copy_to_user(token, stats, &record)?;
```

真实代码还将复制接口的错误统一转换为 `InvalidAddress`。
`audit::stats()` 在同一次借用中取得所有计数，`to_record()` 只转换这些普通值，
不会重新读取全局状态，因此 `total_events == successful_events + failed_events`
等关系属于同一个时刻。用户得到的是一致快照，而非保证返回瞬间仍最新的全局值。

类型 `IpcStatsV1` 固定为 80 字节。无论 `out_size` 为 80、96 还是更大，
`copy_to_user` 都只接收一个此类型的值，所以较大缓冲区的尾部保持不变。

## 8. 为什么成功查询不写入审计

若每次成功读取都追加一条事件，监控程序可能每次追到尾部又制造新的尾部事件，
循环读取就无法结束；查询统计也会不断改变统计值。

本实现成功时直接返回，失败才记录 `AUDIT_OP_AUDIT_READ` 或 `AUDIT_OP_IPC_STAT`。
没有调用 `preflight/complete`：控制查询不需要管道配额，且自己的错误路径已有专用审计入口。
普通 IPC 的授权或配额预检查失败接线仍由集成阶段处理。
