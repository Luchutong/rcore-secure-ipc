## 1. 测试要证明什么

日志可以看作一列带序号的事件。内核只保留最后 `C` 条，读取者自己保存已处理的最后一个
序号 `cursor`。本组测试验证：读取不会消费日志；落后的读取者能发现覆盖；统计与实际
保留的事件一致。最终新增用户程序为 `user/src/bin/audit_test.rs`。

测试既检查数据，也检查副作用。例如返回序号正确、但读取后偷偷增加 `total_events`，
仍然属于失败；输出了 `GAP_BEFORE`、但实际丢掉的是最新事件，也属于失败。

当前代码已具备审计存储、602/603 路由、用户 API、CLI 和初步测试。因此本设计复用现有
入口，补充边界与精确断言，不需要新增“清空日志”或“注入事件”的生产系统调用。

## 3. 独立测试的运行条件

### 3.1 不依赖 A/C 的事件来源

使用有效统计缓冲区，调用以下现有接口：

```rust
// 伪代码：stats_slot 是测试独占的、页内有效的 IpcStatsV1。
let ret = unsafe {
    audit::raw::ipc_stat(stats_slot, core::mem::size_of::<IpcStatsV1>(), 1)
};
assert_eq!(ret, -(audit::EINVAL as isize));
```

`flags = 1` 违反 ABI v1，内核在复制用户内存前返回 `-EINVAL`，并写入一条失败事件。
每次调用应恰好产生一条记录：`operation = 6`、`errno = 22`、`result_value = 0`。
这个事件来源只依赖 D 已实现的 603，不使用信号、管道或资源耗尽。

事件生成器 `emit_failures(n)` 必须检查每次返回值。先用 S01 验证单次调用确实“恰好记一次”，
再把它作为后续用例的输入；否则重复记账可能被错误地当作环形覆盖正常。

成功的 `audit_read` 和 `ipc_stat` 不生成事件，不能拿它们测试 `successful_events` 增长。
成功计数的正向覆盖放在主机层，通过真实 `audit::record` 传入构造的 `IpcRequest` 和 `Ok`。
这不代表真实管道或信号已经接入，相关联合测试仍由 A/C 集成后完成。

### 3.2 初值未知，写入者必须可控

QEMU 用例由拥有读取权限的进程运行，当前建议 UID 0。`stat` 返回 `-EPERM` 应报告权限
前置条件不满足并失败，不能把全零初始化结构当作有效快照。

每个变更阶段重新获取起始快照，不假定全局日志为空，不依赖用例顺序、固定 PID 或 UID。
`getpid()` 在测量区间开始前取得，用于核对测试生成事件的来源。

精确增量要求：采样起点到终点之间没有其他审计写入者。测试主体不 `fork`，不创建管道，
也不把输出重定向到将来会被 C 审计的管道。把进度输出安排在采样区间外，建议延迟至各
场景完成后统一打印；底层测试始终直接调用审计 API。

统计增量只能解决“初值未知”，不能排除并发写入。将来 A/C 合入后，若精确计数不符，应
打印序号区间和来源 PID/操作，报告意外事件，而不是放宽成 `>=` 或当作通过。
并发压力环境另测单次快照不变量、单调性与缺口检测，不复用这里的精确 N 条假设。

### 3.3 B 未合入前的有效用户缓冲区

当前 `mm::copy_to_user` 仍调用 `translated_refmut`，不能保证跨页结构复制正确。
即使用户虚拟范围整体有效，一条 80 字节记录跨越两个物理页也可能出问题。

实现 `audit_test` 时，安排两个静态、独占的测试缓冲区：

- 记录区：`#[repr(C, align(4096))]`，含 34 条记录，内容共 2720 字节，位于同一页内。
  一次最多请求前 33 条，第 34 条用作哨兵。结构对齐后的总大小为 4096 字节。
- 统计区：另一个页对齐的静态区域，存放一个 80 字节结构和尾部哨兵。

测试开始时检查实际地址对齐和数据末端仍在同一页内。静态缓冲区只建立一次独占访问，
将必要 `unsafe` 限定在辅助函数内；不要在多个函数同时保留可变引用。
不要将两个 4096 字节对齐对象放到仅 8 KiB 的用户栈上。

这是本轮测试的受控有效输入，不是对 B 页表检查的替代或修复。非法页、不可写页、跨页
失败和真实部分复制失败继续放在联合安全验收中。

## 4. 从契约推导预期值

以下符号用于描述一次采样到写入后的状态：

| 符号 | 含义 |
| --- | --- |
| `S0` / `S1` | 写入前 / 写入后的统计快照 |
| `C` | `S0.capacity`，必须经 603 查询，不硬编码为 256 |
| `R0` | `S0.retained` |
| `N0` | `S0.next_sequence`，下一条待分配的序号 |
| `F` / `N` | 一份快照的 `first_sequence` / `next_sequence` |
| `M` | 本阶段实际发出的、均返回 `-EINVAL` 的调用数 |
| `L` | 当前实现的单批上限 32；这是本项目回归参数，不是从 capacity 推导的值 |

在没有其他写入、没有序号耗尽、所有注入均被接受的条件下：

```text
S1.capacity            = C
S1.retained            = min(C, R0 + M)
Δtotal_events          = M
Δfailed_events         = M
Δsuccessful_events     = 0
Δoverwritten_events    = max(0, R0 + M - C)
S1.next_sequence       = N0 + M
S1.first_sequence      = S1.next_sequence - S1.retained
```

每份快照还要满足 ABI 约束及当前“只追加、只覆盖、无清空”实现的更强不变量：

```text
capacity > 0
retained <= capacity
total_events == successful_events + failed_events
total_events == retained + overwritten_events
next_sequence == total_events + 1
next_sequence - first_sequence == retained
retained == 0 => first_sequence == next_sequence
```

同时检查 `abi_version == 1`、`struct_size == 80`、`flags == 0` 和 `reserved0 == 0`。
用检查过的加减法计算期望值，先确认 `next_sequence >= 1` 再取尾游标 `N - 1`。
`u64::MAX` 序号耗尽属于独立极限测试，不靠 QEMU 注入海量事件模拟。

读取预期以逻辑序号集合为准，不复制内核的 `head/index/% capacity` 算法：

```text
保留集合 = [F, N) 中的整数序号
候选集合 = 保留集合中严格大于 cursor 的元素
预期返回 = 候选集合的前 min(requested_capacity, L) 项
```

有返回记录时，`GAP_BEFORE` 当且仅当 `cursor + 1 < F`；只允许第一条带该位。
`cursor == u64::MAX` 或请求容量为 0 时返回空，不计算溢出的 `cursor + 1`。
该数学预期来自保留语义，能检出数组下标、首尾偏移和分页错误。

## 5. 游标测试矩阵

QEMU 准备：保存 `c0 = S0.next_sequence - 1`，注入 `K = min(C, 2L + 1)` 条失败事件，
然后冻结测量阶段的写入。当前 C=256 时 K=65。这 K 条新事件均应保留，预期序号为
`c0+1 .. c0+K`；不能把之前已有的记录算入本场景。
要求 `C > L` 才能验收跨批次场景；若未来配置不满足，明确报告配置不支持该场景，不能静默通过。

| 编号 | 步骤 | 精确断言 | 验证层 |
| --- | --- | --- | --- |
| C01 | 空日志读取；另测任意状态的尾游标读取 | 新启动主机环为空、返回 0；QEMU 传 `stat.next_sequence-1` 返回 0，不要求全局为空 | 主机空态 + QEMU 尾态 |
| C02 | 用 `c0`、容量 7 连读两次，不推进游标 | 两次均为最早的 7 条新记录，逐字段一致，统计不变 | 主机 + QEMU |
| C03 | 从 `c0` 用容量 7 逐批读到初始目标尾部，再读一次 | 每批严格连续、首条为上次末条+1；累计 K 条；末次为 0，无遗漏/重复 | 主机 + QEMU |
| C04 | 两个逻辑读取者 A/B 都从 `c0` 开始；A 先前进两批，再启动 B | B 仍可读到第一批；A/B 最终读到相同完整序号区间 | 主机 + QEMU 单进程两个变量 |
| C05 | 相同 `c0` 分别请求 0、1、31、32、33 条 | 返回 `min(K, request, 32)`；逐项匹配预期；返回范围以外的哨兵不变 | 主机 + QEMU |
| C06 | 传尾游标、尾后有限游标和 `u64::MAX` | 都返回 0，输出保持哨兵状态，统计不变，不发生回绕 | 主机 + QEMU |
| C07 | 追到尾部并读得0后，保存游标，再注入1条并继续读取 | 恰好读到旧尾部+1这一条；继续用新游标读得0，空读不冻结后续增量读取 | 主机 + QEMU |

“逐字段一致”包含时间戳和元数据，不比较 Rust 结构的未初始化填充字节。
标志用位掩码检查已知 `GAP_BEFORE`，保留未知位，不要求所有未来标志永远为 0。
当前这批新记录没有缺口，所有记录的 `GAP_BEFORE` 都应为 0。

翻页必须用最后一条 `sequence` 更新游标；不能用 `cursor += count`，覆盖后两者不等价。
返回值先检查 `ret >= 0`、`ret <= records.len()`、`ret <= L` 再转成 `usize`。
正数批次必须推进游标；短批次本身不是终止条件。设最多 K+1 次读取的预算，即便每批
只有一条也能结束；达到预算或不前进直接失败，不能留下无限循环。

## 6. 覆盖测试矩阵

| 编号 | 步骤 | 精确断言 | 验证层 |
| --- | --- | --- | --- |
| O01 | 全新主机环依次达到 C−1、C、C+1 条 | 覆盖累计分别 0、0、1；首次覆盖后保留 2..C+1，first=2 | 主机；QEMU 只做可到达的补满阶段 |
| O02 | 从快照 R0 补写 C−R0 条，采样满状态，随后再写 1 条 | 补满不增加覆盖；多写 1 条才使 first、next、覆盖各+1，retained=C | 主机 + QEMU |
| O03 | 保存新起点尾游标 c0，注入 C+1 条 | 全部保留记录为 `N0+1 .. N0+C`；原 cursor 下一条 N0 已丢失；总数与覆盖增量按第4节公式核对 | 主机 + QEMU |
| O04 | O03 后分别以 F−2、F−1、F 为游标读取 | 首条分别 F、F、F+1；首条 GAP 分别有、无、无，其余记录无 GAP | 主机 + QEMU |
| O05 | 分别以旧 c0 和边界 F−1 多次读取 | 同一事件在不同读取视图的 GAP 不同；旧游标重读仍报告缺口，边界读取仍无缺口 | 主机 + QEMU |
| O06 | 从另一份 S0 注入 2C+3 条，遍历全部保留事件 | 精确保留最后 C 条；顺序连续；累计覆盖按公式增加，不因下标绕回重复旧数据 | 主机 + QEMU |
| O07 | 重新准备C03的输入，只读第一批；插入C+1条，再以保存的游标读 | 下一批从新 first 开始，首条带 GAP；用实际末序号继续读，不误认为下一条仍连续 | 主机 + QEMU 单线程交错 |

O04 需要 `F >= 2`，由 O03 保证；这些边界读取之间不再写入事件。
O05 证明 GAP 是“读取者缺口”，不是永久写回某条事件的属性；也不是整个系统只报告一次。
`after_sequence=0` 在发生历史覆盖、F>1 后仍从 F 返回，当前 ABI/内部设计规定首条带 GAP。
加入此边界断言，避免把 0 当作“隐藏覆盖提示”的特殊值。

O01 的全新空态必须放在独立主机测试进程中，不通过给生产内核增加 reset 接口实现。
QEMU 可能在启动测试前已经满环，因此 R0=C 时补满阶段只写 0 条，不能据此宣称验证了
“从 C−1 到 C”；该转换由独立主机场景负责。

例如容量 C=4，从空环写入 1、2、3、4 后没有覆盖；写入 5 后保留 2、3、4、5，覆盖数为1。
此时 cursor=0 需要的下一条是1，已被丢弃，因此返回2并带 GAP；cursor=1 需要的下一条是2，
仍保留，因此返回2但不带 GAP。这个一条之差能检出把 `<` 错写成 `<=` 的边界错误。

## 7. 统计测试矩阵

| 编号 | 步骤 | 精确断言 | 验证层 |
| --- | --- | --- | --- |
| S01 | 采样，非法 flags 查询一次，再采样和读取该事件 | 返回−22；total/failed/next 各+1，successful不变；新增且仅新增一条op=6、errno=22记录 | 主机 + QEMU |
| S02 | 各阶段采样；检查版本、布局和第4节不变量 | 每份快照自洽；两个 ABI 结构 size 均为80；不得混用不同采样时刻的字段 | 主机 + QEMU |
| S03 | 注入 M 条失败记录，在未满/已满状态分别采样 | failed 增 M，successful 不变；保留和覆盖增量准确，不只检查“增加” | 主机 + QEMU |
| S04 | 构造两条成功 IPC 事件，再构造三条失败事件 | Δsuccessful=2、Δfailed=3、Δtotal=5；成功记录errno=0，失败结果=0 | 主机真实 record 入口 |
| S05 | S04 后继续写超过 C 条失败事件，覆盖掉成功记录 | 即便保留记录全部失败，历史 successful 仍为原值；累计数不能按保留数组重新计算 | 主机；QEMU验证累计不减 |
| S06 | 同一测量窗口内重复成功 stat、非空 read、尾部 read、零容量 read 各多次 | 所有操作返回成功；测量前后所有统计字段相同；固定尾部最终返回0 | 主机 + QEMU |
| S07 | 合法统计输出长度80，再用长度96并设置16字节尾部哨兵；另传size=79 | 合法调用只写前80；size=79返回−22、恰好新增一次失败、输出不作为有效快照读取 | 主机 + QEMU |
| S08 | 连续启动 audit_test 两次，不重启 QEMU | 第二次仍通过增量断言；不清空日志，不要求首次sequence为1 | QEMU |

S01 对注入事件额外检查：`subject_pid` 为当前测试PID，`object_id=0`，
`object_owner_uid=AUDIT_UID_UNKNOWN`，`requested_amount=0`，`result_value=0`，
`reserved0=reserved1=0`，`abi_version=1`，`record_size=80`。
已知以 UID 0 运行时再断言 `subject_uid=0`；不把一般运行时 UID 猜成固定值。
时间戳只要求符合来源和非倒退的测试条件，连续调用可以在同一毫秒，不能断言严格递增。

S06 需在确有记录时执行非空读取，不能只测空尾部。重复次数可取8，区间内不输出进度。
用静态数据快照或字段拷贝比较，不假定用户 ABI 类型已实现 `PartialEq`。

S04 的成功事件使用构造的 PipeRead/PipeWrite 请求，覆盖 `Ok(0)` 和 `Ok(60)`；
合法的0字节结果仍是成功。测试直接验证真实审计转换和存储，并不执行实际管道操作。

测试中假定“我先运行”。仅使用 `--test-threads=1` 不能保证测试顺序，也不会清空状态。
新生命周期场景只通过现有 `record`、`snapshot`、`stats` 等入口驱动真实模块。

建议用户测试辅助函数：

```text
load_stats()                         // 检查返回码、ABI与快照不变量
emit_failures(count)                  // 每次必须返回-EINVAL
assert_failure_delta(before, after, m)// 使用第4节数学期望
read_checked(buffer, cursor)          // 检查负值、长度、序号和记录布局
assert_injected_record(record, pid)   // 检查op/errno/来源/保留字段
assert_same_stats(before, after)      // 成功查询无副作用
drain_expected_range(cursor, end)     // 逐条核对、固定上界、有循环预算
```

建议执行次序：布局/前置条件 → S01生成器校准 → C01～C07 → S06 → O02～O07 →
S02/S03/S07复核 → 汇总。主机层另做O01、S04/S05。
对 C 和 `2C+3` 用 checked 算术，并设置每阶段最多4096次注入的测试预算；若未来容量过大，
以明确的配置错误退出，不静默截断注入数量、不把覆盖未发生当通过。

每个场景只保存固定批次和少量统计，遍历时逐条验证，不把全环记录积累到用户堆或栈。
哨兵检查只比较本轮未返回的槽位，使用明确初始化的值。

建议每个场景具有固定编号。以下仅为后续实现的输出示例：

```text
[audit_test][C03] PASS cursor pagination
[audit_test][O03] FAIL overwritten delta: expected=257 actual=256
[audit_test] failed
```

断言失败时非零退出或使用现有用户 panic 路径；不得仍返回0。
成功时最终只输出一次 `audit_test passed!` 并返回0。
报告包含用例ID、输入游标、前后first/next/retained/计数、期望与实际值；不要打印地址或载荷。
