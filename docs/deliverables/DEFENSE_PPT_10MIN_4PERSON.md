# 答辩 PPT 设计与逐页讲稿（10 分钟四人版）

> 本方案是正式答辩主版本。D 为主讲与统筹人，A/B/C 分别讲解本人负责的安全模块。
> [DEFENSE_PPT.md](DEFENSE_PPT.md) 保留为现场临时缩短时长时使用的 5 分钟备用版。

## 1. 总体设计思路

整场汇报采用“主讲人串联 + 三位模块负责人接力”的结构，而不是平均切成四段彼此独立的个人汇报。

- **D 为主讲人**：负责项目背景、总体架构、人员交接、综合测试和最终结论，保证前后口径统一。
- **A 为模块发言人**：负责凭据与信号授权，回答“谁有权进行 IPC 操作”。
- **B 为模块发言人**：负责用户地址安全，回答“内核如何安全接收用户参数”。
- **C 为模块发言人**：负责资源配额与性能，回答“如何限制资源占用并控制额外开销”。
- D 在最后介绍审计模块，回答“如何记录、追踪和验证安全行为”，再统一收束测试与成果。

四人从开场起一起站在台前，按 D→A→D→B→D→C→D 的顺序发言。D 不必在每次交接时重复背景，
只用一句话指出“上一模块解决了什么、下一模块还要解决什么”。全程只使用一个翻页器，默认由 D
控制；A/B/C 讲到标有本人姓名的页面时，由 D 配合翻页，避免交换设备造成停顿。

- 每个模块页右上角固定显示 `A / B / C / D` 小标签，让老师立即知道该页负责人。

### 第 2 页：教学 IPC 已能通信，但安全边界仍需补齐

**主讲：D｜45 秒**

页面左侧放三句定义，右侧放四类风险：

- rCore：用 Rust 编写、面向 RISC-V 的教学操作系统。
- IPC：进程之间交换数据、同步状态和发送控制事件的机制。
- 第七章通过管道与信号把进程、文件描述符和系统调用连接起来。
- 原始教学实现仍面临越权、坏指针、资源耗尽和行为不可追踪四类风险。

**备注讲稿：**

“rCore 是面向 RISC-V、使用 Rust 实现的教学操作系统。IPC 是进程间通信，在第七章中，
管道负责数据传输，信号负责异步控制，它也是连接进程管理、文件描述符和系统调用的重要场景。
Rust 能提高内核内部的内存安全，但系统调用收到的仍是用户给出的地址和参数；同时，教学实现
也没有完整覆盖身份、配额和审计。因此我们的工作不是重新实现 IPC，而是补齐它的安全闭环。”

### 第 3 页：四层防线构成一条可验证的安全 IPC 链

**主讲：D｜50 秒**

插入 [fig-06-architecture.png](figures/fig-06-architecture.png)，旁边只保留四个关键词：

- B：安全复制，非法地址返回 `EFAULT`。
- A：凭据与策略，越权操作返回 `EPERM`。
- C：事务式配额，失败能够回滚。
- D：有界审计，行为能够追踪。

页脚写：公共 ABI 冻结后按 **B→A→C→D** 正式集成。

**备注讲稿：**

“整体调用链分为四层。先由 B 安全接收用户参数，再由 A 判断身份与权限，C 对资源做预留、
提交或回滚，最后由 D 记录审计结果。我们先冻结系统调用号、错误码和共享数据结构，减少四个
分支反复改接口；正式集成按 B、A、C、D，是因为后层依赖前层提供的安全输入、授权结果和资源
状态。下面先请 A 介绍身份与授权。”

**D→A 交接句：**“安全调用首先要回答‘谁能做’，这一部分由 A 介绍。”

### 第 4 页：最小凭据模型让授权不再只依赖 PID

**主讲：A｜55 秒**

页面画一个简洁流程：`Credentials(uid, capabilities) → policy → Allow / EPERM`，列出：

- fork 继承凭据；普通进程只能降权，不能自行恢复 root。
- 自发送、同 UID、root、`KILL` capability 可以发送信号。
- 其他跨 UID 信号被拒绝并留下审计记录。

**备注讲稿：**

“我负责凭据与授权模块。我们给每个进程加入最小凭据，包括 UID 和 capability 集合，并在
fork 时继承。信号发送不能只看 PID，因为知道目标 PID 不等于拥有控制权限。策略允许进程给
自己或同 UID 进程发送，root 和具备 KILL capability 的进程也可以发送，其他情况统一返回
EPERM。普通进程的 setuid 只允许降权，避免先降权后再自行恢复 root。”

---

**主讲：A｜45 秒**

整页插入 [module-a-auth-results.png](figures/module-a-auth-results.png)，不再叠加标题、图标或说明文字。
实际 QEMU 输出保存在 [module-a-auth-test-20260915.log](logs/module-a-auth-test-20260915.log)，答辩时口头说明

**备注讲稿：**

“`cred_test` 同时覆盖允许和拒绝路径：同 UID、root 和 capability 放行，普通跨 UID 请求
返回 EPERM。测试还检查 fork 后的凭据继承和降权规则。授权失败不是系统故障，而是预期安全
行为，所以对应异常在测试汇总中也记为 PASS；同时拒绝事件进入审计，便于后续定位。我的模块

### 第 6 页：先验证完整范围，再按页安全复制

**主讲：B｜55 秒**

页面画三步流程：`用户地址与长度 → 页表逐页检查 U/R/W → copy_from/to_user`，列出：

- 检查空地址、内核地址、溢出、未映射页和访问权限。
- 跨页对象按实际映射分段复制，不假定物理连续。
- 整个范围验证通过后才写入，避免半写入状态。
- 错误统一返回 `EFAULT`，不允许内核 panic。

**备注讲稿：**

“我负责用户地址安全模块。Rust 只能保证已经建立的安全引用，而系统调用入口接收的是用户态
裸地址，不能直接转成内核引用。我们先检查地址范围和整数溢出，再逐页检查页表中的用户、可读、
可写标志，最后按页复制。输出数据采用先完整验证再写入，避免前半段已经修改、后半段才发现
错误。所有坏地址都返回 EFAULT，让内核继续运行。”

### 第 7 页：八类坏指针全部返回 EFAULT，内核继续运行

**主讲：B｜45 秒**

整页使用 [fig-02-security-matrix.png](figures/fig-02-security-matrix.png)，右下角突出 `8/8 PASS`。

**备注讲稿：**

“`badptr` 覆盖空指针、内核地址、极高地址、长度溢出、未映射页、跨页缺页、只读输出和跨页
只读等八类输入，结果全部按预期返回 EFAULT。关键不只是得到错误码，而是每次非法调用之后
测试程序还能继续执行，说明错误被系统调用边界吸收，没有引发内核崩溃。这一模块为后面的授权、
配额和审计提供了可信输入。”

**B→D 交接句：**“地址安全解决了‘能否安全访问’，接下来还要限制‘一个进程能占用多少’。”

**D 串场句：**“下面请 C 介绍 IPC 配额以及失败路径为什么必须能够回滚。”

### 第 8 页：事务式配额让资源失败不泄漏状态

**主讲：C｜55 秒**

页面用状态箭头表示：`preflight → reserve → create → commit`，失败分支指向 `rollback`。列出：

- 每进程最多 32 个打开文件、16 个管道端点。
- 一条管道占用两个端点；普通 FD 与管道端点分开记录。
- 创建前原子预留，任一步失败都回滚。
- close、dup、fork 路径共同维护配额状态。

**备注讲稿：**

“我负责资源治理模块。仅在创建完成后再计数会产生竞态，所以我们采用事务模型：先检查并原子
预留额度，创建成功后提交，任何中途错误都回滚。每个进程最多打开 32 个文件、占用 16 个管道
端点，一条管道需要两个端点。`pipe_fd_mask` 区分普通文件和管道端点，close、dup 和 fork
都会同步维护状态，从而避免失败路径或并发路径造成计数泄漏。”

---

### 第 9 页：配额可恢复，额外检查未造成数量级回退

**主讲：C｜50 秒**

左侧放配额测试结论：7 组场景通过、耗尽后返回 `EMFILE/ENOSPC`、关闭端点后可再次创建。
右侧使用 [fig-04-performance.png](figures/fig-04-performance.png)。

**备注讲稿：**

“`quota_test` 覆盖耗尽、恢复、dup、close、fork 和失败回滚等七组场景，资源达到上限时返回
EMFILE 或 ENOSPC，关闭端点后能够再次创建。性能方面，我们在 QEMU 中连续执行两万轮管道
创建和关闭，各运行五次并取中位数；基线是 647 毫秒，安全版本是 746 毫秒，观测增加约
15.3%。它不是硬件级精密微基准，但足以说明没有从毫秒级退化到十倍以上的数量级回退。”

**C→D 交接句：**“资源现在能够被限制和恢复，最后还需要让关键行为能够被追踪和整体验证。”

### 第 10 页：有界审计在可追踪性与抗 DoS 之间取平衡

**主讲：D｜55 秒**

页面使用 [fig-05-audit-output.png](figures/fig-05-audit-output.png)，旁边列出：

- 固定 80 字节 ABI，序号游标读取，不消费日志。
- 环形缓冲区最多保留 256 条，旧记录覆盖时可发现缺口。
- 普通用户读取自身记录，特权用户可查看全局统计。
- `auditctl stat` 与 `auditctl read <cursor>` 提供真实工具入口。

**备注讲稿：**

“审计模块采用固定 80 字节记录和单调序号。读取使用游标，不删除原日志，因此多个观察者可以
独立查看；缓冲区最多保留 256 条，防止攻击者用日志耗尽内核内存，覆盖发生时可以通过序号缺口
和统计值发现。权限上，普通用户只能读取相关记录，特权用户可查看全局信息。我们还实现了
`auditctl`，不是只在单元测试里调用内部函数，而是通过真实系统调用读取统计和事件。”

### 第 11 页：宿主测试、QEMU 与压力实验形成三层证据

**主讲：D｜60 秒**

左侧放 [fig-01-ci-summary.png](figures/fig-01-ci-summary.png)，右侧放
[fig-03-audit-stress.png](figures/fig-03-audit-stress.png)。页面底部写：

- 宿主测试：28/28，验证策略和数据结构逻辑。
- QEMU：28 个预期成功 + 4 个预期异常 = 32/32。
- 压力：6×128=768 个事件，缓冲区最多保留 256 条。

**备注讲稿：**

“我们把验证分成三层。宿主测试 28 项，快速检查授权策略、审计环和配额事务等纯逻辑；它使用
替身环境，不能替代真实页表。QEMU 用户态测试经过系统调用、页表和调度器，28 个预期成功加
4 个预期异常，共 32 项全部通过。四个异常是对非法地址和权限拒绝的预期结果，因此也属于
PASS。压力测试由 6 个工作进程各产生 128 个事件，共 768 个，而内核始终最多保留 256 条，
证明审计内存占用有界。所有证据由 CI 固化。”
