## 2. P0：必须熟练回答的问题

### P0-01：这个项目到底解决了什么问题？

**建议回答：**

原版 rCore 第七章已经能做管道、信号等进程间通信，但“功能可用”并不代表“安全边界完整”。
我们围绕 IPC 路径补齐了可信输入、身份授权、资源治理和行为审计四层能力，使系统从“能通信”
提升为“安全、可控、可追踪、可验证地通信”。

**追问要点：**

- B 解决“用户给进来的地址是否可信”；A 解决“这个进程是否有权操作”；C 解决“资源是否会被耗尽或泄漏”；D 解决“安全决策和结果是否可追溯”。
- 项目面向 rCore 第七章教学内核，并非完整的生产级安全操作系统。

### P0-02：模块 D 在整个项目中的位置是什么？

**建议回答：**

模块 D 是安全路径的“证据层”，不替代 B/A/C 做安全决策。它把 IPC 操作的主体、对象、操作类型、
结果、错误码和时间转换为结构化审计事件，供有权限的用户态工具读取和验证。

**追问要点：**

- D 在安全门面的 `complete` 阶段记录成功或失败结果；A 的授权拒绝、C 的配额拒绝也会被记录。
- 对于 B 在用户地址校验阶段发现的错误，会以失败事件形式记录。
- 因此 D 记录的是“安全路径实际发生了什么”，而不是只在正常路径打印调试信息。

### P0-03：D 模块具体实现了哪些内容？

**建议回答：**

D 模块实现了固定容量审计环形缓冲区、两个审计系统调用、用户态 `auditctl` 工具，以及配套的宿主、
QEMU、压力和性能测试。内核接口是 `audit_read`（syscall 602）和 `ipc_stat`（syscall 603）。

**追问要点：**

- `audit_read` 按游标读取事件；`ipc_stat` 返回容量、保留数量、序号范围、成功/失败/覆盖计数。
- 用户态 `auditctl stat` 显示统计，`auditctl read [after_sequence]` 按页读取日志。
- 代码入口主要是 `os/src/security/audit.rs` 与 `os/src/syscall/security.rs`。

### P0-04：为什么不能仅使用 `println!` 或内核日志完成审计？

**建议回答：**

普通打印日志适合调试，但不是稳定的审计接口：它不能分页查询、不能给多个读取者独立读取、难以
检查覆盖，也可能无限增长。D 模块提供了固定 ABI、序号、游标、统计快照和权限控制，因此用户态
程序能够可靠地验证，而不是解析一段临时文本。

**追问要点：**

- 审计记录采用 `#[repr(C)]` 的固定 80 字节结构，内核和用户库都有大小断言。
- 操作类型使用稳定整数编号，不直接暴露 Rust 枚举内部布局。
- 审计记录保存元数据，不保存管道载荷、用户字符串、裸指针或内核地址。

### P0-05：为什么审计缓冲区必须有界？容量是多少？

**建议回答：**

若审计事件持续累积而动态分配内存，攻击者可以通过制造事件把内存耗尽，造成审计本身成为 DoS
入口。因此本实现采用固定容量为 256 条的环形缓冲区，满后覆盖最旧记录，内存占用始终有上限。

**追问要点：**

- 每条用户 ABI 记录固定为 80 字节；256 条对应的用户可见记录量级约为 20 KiB。
- 用户态不能假定容量永远是 256，应通过 `ipc_stat` 查询；256 是当前实现配置。
- 单次 `audit_read` 最多返回 32 条，避免由用户参数触发无界内核栈或复制工作量。

### P0-06：日志覆盖后是不是会悄悄丢失数据？

**建议回答：**

旧记录确实可能被覆盖，但不会悄悄发生。每条事件有单调递增序号，统计中有
`overwritten_events`，当读取者游标之前的事件已被覆盖时，返回批次第一条会带
`GAP_BEFORE` 标志。因此读取工具知道自己错过了哪些历史区间。

**追问要点：**

- 审计的目标是“固定内存 + 可检测的数据缺口”，不是承诺永久保存所有事件。
- 读取者应以最后一条成功读取记录的 `sequence` 作为下次游标，不能简单用“游标加条数”推进。
- `GAP_BEFORE` 是读取视图属性：同一条记录对不同旧游标可能有不同的缺口含义，不会永久写回原事件。

### P0-07：审计会不会改变原 IPC 操作的结果？

**建议回答：**

不会。审计只观察并记录 IPC 的最终 `Ok` 或 `Err` 结果，原系统调用的返回值不被审计逻辑替换。
这是通过固定内存环形缓冲区和“记录结果后原样返回 outcome”的结构保证的。

**追问要点：**

- 审计写入不依赖动态分配；即使序号到达 `u64::MAX`，也只是停止接受新审计事件，不影响原 IPC 操作。
- 这体现了“审计不能成为业务功能的单点失败源”。

### P0-08：如何防止读取审计日志导致无限自反馈？

**建议回答：**

成功的 `audit_read` 和 `ipc_stat` 不会向同一个环形缓冲区再写入事件。否则监控工具每读一条日志就
新增一条日志，会永远追不上日志尾部。权限拒绝、非法参数和坏指针等失败的审计调用仍会记录，
因为它们本身是安全相关事件。

**追问要点：**

- 成功控制调用“不自记录”保证可读性；失败控制调用“要记录”保证攻击和误用可观测。
- 失败只记一次，避免同一失败在多个入口重复写入。

### P0-09：谁能读取审计数据？如何防止审计泄露隐私？

**建议回答：**

`audit_read` 和 `ipc_stat` 只允许 UID 为 0，或拥有 `AUDIT_READ` capability 的进程调用。
无权限者得到 `-EPERM`，不会获得其他进程的日志或统计。记录本身只保留安全元数据，不记录
管道内容、用户缓冲区、字符串、内核地址或物理地址。

**追问要点：**

- PID 和 UID 用于审计主体识别；资源使用稳定 `ResourceId`，不用 `Arc` 地址或裸指针。
- 未知资源所有者使用 `u32::MAX`，不能把合法的 root UID 0 误当作未知。

### P0-10：审计系统调用如何防止坏指针使内核崩溃？

**建议回答：**

审计系统调用不直接解引用用户传入的输出指针，而是使用 B 模块的 `copy_to_user` 完成用户地址、
跨页和写权限检查。非法输出地址统一返回 `-EFAULT`，不会触发 kernel panic。

**追问要点：**

- `audit_read` 的零容量请求不访问输出地址；但权限检查仍优先进行。
- `ipc_stat` 先检查 `flags==0` 和输出长度至少 80 字节，再检查地址；非法 flags 不触碰用户指针。
- 若逐条复制时后半段失败，调用者收到 `-EFAULT`，不得推进游标；日志快照仍在内核中，不会因读取失败被删除。

### P0-11：为何要先做审计快照、释放锁后再复制给用户？

**建议回答：**

持有审计缓冲区锁时不能访问用户内存、阻塞或调度，否则临界区过长且容易产生锁顺序问题。
因此内核先在锁内复制一个固定大小、最多 32 条的纯内核快照；锁释放后再转换 ABI 并复制到用户态。

**追问要点：**

- 这也保证 syscall 开始后新产生的事件不会混入本次读取快照。
- 统计快照同样在一次审计锁借用中取得，避免字段来自不同时间点而互相矛盾。

### P0-12：最终综合验证的四类测试分别证明什么？

**建议回答：**

QEMU 回归验证真实内核环境中的四模块联动；宿主测试验证审计 ABI、工具和边界逻辑；多进程压力
验证高负载下有界存储与覆盖语义；性能测试验证安全路径没有出现数量级回退。四者不是重复测试，
而是分别覆盖功能、接口、压力和代价。

**追问要点：**

- QEMU：32/32；Host：28/28；压力：6×128=768，保留上限 256；性能：+15.3%。
- 不能只用 QEMU 替代 Host：Host 更适合细粒度、确定性的 ABI/游标/错误路径验证。

### P0-13：压力测试的最终结果是什么，结论应如何表述？

**建议回答：**

6 个子进程各生成 128 个事件，共 768 个。所有事件都进入累计统计，而固定环形缓冲区最多保留
最新 256 条；最终输出同时验证覆盖计数、序号连续性和进程正常退出。结论是“审计负载不会造成
无界内存增长，覆盖行为可观测”，不是“768 条永久保留在内核中”。

**追问要点：**

- 压力用例使用非法 `ipc_stat(flags != 0)` 生成真实 `EINVAL` 审计失败事件，来源确定、可重复，且不依赖其他模块内部实现。
- 时间仅用于诊断，不设置性能阈值，避免宿主负载波动造成 CI 偶发失败。

### P0-14：性能测试具体怎么做？为什么用中位数？

**建议回答：**

基准固定重复 20,000 次 `pipe → close(read) → close(write)`，在同一 QEMU 环境中运行五次，记录每次
总耗时并取中位数。基线中位数为 647 ms，最终安全 IPC 为 746 ms，约增加 15.3%。取中位数是为了
减少 QEMU 调度和宿主负载偶发波动的影响。

**追问要点：**

- 环境：WSL2、单核 rCore、QEMU 8.2.2、release 构建。
- 每次最终安全路径运行均新增 20,000 个成功审计事件，说明没有误测未接线代码。
- 应说“没有观察到数量级性能回退”，不能说“完全没有性能代价”。

### P0-15：为什么最终集成顺序是 B → A → C → D？

**建议回答：**

B 先保证系统调用边界能够安全处理不可信用户地址；A 再在可信身份上下文上做授权；C 在授权通过后
管理资源预留、提交和回滚；D 最后记录整条路径的结果。D 可以并行开发，但在正式联调时最后接入，
才能审计和验证前面模块的真实联合结果。

**追问要点：**

- 顺序反映依赖关系，不代表四个人必须串行开发。
- 公共 API 预先冻结，各成员在自己的模块内并行实现；正式合并时才按依赖顺序进行。

### P0-16：为什么要冻结公共 API？

**建议回答：**

四人并行开发时，若每个模块自行改变错误码、请求结构、系统调用号或调用顺序，会让集成和测试不断
失效。冻结 `IpcRequest`、`IpcError`、`IpcOperation`、系统调用号和调用顺序后，模块只能通过统一门面
协作，测试、用户库和审计 ABI 就能稳定复用。

**追问要点：**

- 公共 API 变更需要独立 API change PR，并由至少两名非作者成员审核。
- D 不直接访问 A/C 的内部状态；它接收统一的请求和结果，保持模块边界。

## 3. P1：高概率深入追问

### P1-01：`audit_read` 的游标和分页语义是什么？

**建议回答：**

调用者传入已处理的最后一个序号 `after_sequence`，内核返回所有 `sequence > after_sequence` 的保留
记录，按序号递增排列。单次最多 32 条；调用者以本批最后一条序号作为下次游标继续读取。

**追问要点：**

- `after_sequence=0` 表示从当前仍保留的最早记录开始。
- 已到日志尾部或传入 `u64::MAX` 时返回 0。
- 读取是非破坏性的，不删除事件，也不维护内核侧“每用户游标”。

### P1-02：何时设置 `GAP_BEFORE`？

**建议回答：**

当读取者希望读取的下一条序号早于当前仍保留的最旧序号，说明中间事件已经被覆盖。内核从当前最旧
事件开始返回，并只在本批第一条记录设置 `GAP_BEFORE`。

**追问要点：**

- 若游标正好是 `first_sequence - 1`，下一条仍在环中，因此没有 GAP。
- 这个一条之差是覆盖边界最重要的正确性测试点。

### P1-03：为什么 ABI 要有版本号、结构大小和保留字段？

**建议回答：**

审计数据跨内核、用户库和工具传递，必须有可演进的二进制契约。`abi_version=1` 和固定结构大小为
80 字节让旧工具能够拒绝不兼容的新格式；保留字段当前置零，为未来扩展预留空间。

**追问要点：**

- 内核和用户库都对结构大小做编译期断言。
- 新操作类型只能追加稳定编号，不能改写或复用已有编号。

### P1-04：为什么审计记录里使用正 errno，而 syscall 返回负 errno？

**建议回答：**

系统调用返回值遵循 rCore 的负 errno 约定，例如 `-EFAULT`。审计记录的 `errno` 是结构化字段，保存
正 errno，例如 14；成功时为 0。这样错误码和结果值不会混淆。

**追问要点：**

- 失败记录的 `result_value` 强制为 0。
- 合法的 0 字节读写仍是成功，判断依据是 `errno==0`，不是 `result_value` 是否为 0。

### P1-05：如何保证统计值是一致快照？

**建议回答：**

`ipc_stat` 在一次审计缓冲区借用中读取 capacity、retained、首尾序号以及成功/失败/覆盖计数，再把
这份普通值快照复制给用户。不会把不同时间点的字段拼到同一个统计结构里。

**追问要点：**

- 关键不变量：`retained <= capacity`，`total = success + failed`，`next - first = retained`。
- 空缓冲区时 `first_sequence == next_sequence`。

### P1-06：记录的事件字段有哪些？为什么不记录完整数据？

**建议回答：**

每条记录包括 ABI 版本、操作编号、errno、主体 PID/UID、稳定对象 ID、对象所有者 UID、请求量、
结果量、序号和启动后毫秒时间。它记录安全决策需要的元数据，不记录管道内容、用户缓冲区或内核地址，
以避免审计接口变成信息泄露接口。

**追问要点：**

- 时间是“内核启动后的毫秒数”，不是 Unix 墙上时间。
- `object_id` 是稳定资源编号，禁止以 Rust `Arc` 地址、裸指针或物理地址替代。

### P1-07：多进程压力下如何保证并发安全？是否支持多核？

**建议回答：**

当前 rCore 配置是单核，审计全局状态使用 `UPSafeCell` 在短临界区内串行化访问。多进程压力中的进程是
调度交错执行，但每次环形写入、序号分配和计数更新在同一临界区完成，因此统计不会半更新。

**追问要点：**

- 当前不宣称支持 SMP；若扩展多核，需要替换同步原语并重新审查锁顺序、内存可见性和性能。
- 审计锁期间不访问用户内存、不阻塞、不调度。

### P1-08：D 如何确保一条 IPC 不会被重复审计或遗漏？

**建议回答：**

安全门面的 `preflight` 在授权或配额拒绝时直接记录一次失败；成功取得许可后，`complete` 负责提交或
回滚资源并记录一次最终结果。审计控制 syscall 的失败走专用入口且只记一次，成功读取不自记录，
从而避免重复和自反馈。

**追问要点：**

- 审计范围是进入 Secure IPC 门面的操作及可安全构造请求的失败。
- 未知 syscall、普通页故障、非 IPC 异常和管道载荷不属于 v1 强制审计范围。

### P1-09：Host 28/28 具体覆盖了什么？

**建议回答：**

宿主测试分为三组：审计 ABI、事件转换和环形统计 7/7；`auditctl` 的参数、分页、游标和异常数据
12/12；审计 syscall 权限、地址边界、快照与复制失败 9/9，合计 28/28。

**追问要点：**

- Host 测试快、确定性高，适合精确检查边界条件。
- 它不替代 QEMU，而是和 QEMU 的真实内核环境验证形成互补。

### P1-10：QEMU 32/32 中的“预期异常”通过是什么意思？

**建议回答：**

预期异常用例不是要求应用正常返回，而是要求内核按照规定终止违规程序，并保持测试框架和内核继续
运行。因此“异常程序以预期信号结束”也属于测试通过，最终是 28 个预期成功和 4 个预期异常，共 32/32。

**追问要点：**

- 这能区分“安全地拒绝恶意行为”和“内核 panic 导致整个测试失败”。

### P1-11：为什么性能测试不用固定阈值放进 CI？

**建议回答：**

性能受 QEMU、宿主调度、缓存和构建环境影响较大。若把一个细小耗时阈值设成 CI 的硬失败条件，容易
产生偶发失败。因此性能程序参与构建并用于固定方法的人工复测，CI 主要验证功能与安全语义。

**追问要点：**

- 为降低波动，使用 release 构建、固定 20,000 次工作量、五次运行和中位数。
- 未来可增加更稳定的专用性能环境和统计置信区间。

### P1-12：为何说 +15.3% 是常数级，而不是“性能很好”？

**建议回答：**

这里的“常数级”是指安全检查、配额处理和审计写入没有引入随迭代次数急剧增长的新复杂度；在固定
工作负载中表现为固定比例的额外代价。15.3% 是可见开销，应诚实说明，而不是把它美化为零成本。

**追问要点：**

- 当前仅覆盖 pipe 创建与关闭，不代表管道读写吞吐、SMP 或真实硬件上的全部场景。
- 结论是“未观察到数量级回退”，不是“已经完成性能最优化”。

### P1-13：为什么审计读取要限制权限，但授权拒绝本身还要记日志？

**建议回答：**

读取权限避免普通进程窥探全局 IPC 元数据；同时，未授权读取是值得关注的安全行为，应该留下失败事件。
这样既不泄露日志内容，也保留了对越权尝试的可观测性。

**追问要点：**

- 这是“拒绝信息不外泄，但拒绝行为可追踪”的设计。
- 失败事件可被管理员通过具有 `AUDIT_READ` 的工具查看。

### P1-14：为什么不在内核里为每个审计读取者维护游标？

**建议回答：**

为每个读取者保存状态需要处理进程退出、权限变化、资源回收和无限数量读取者的问题。由用户态保存
最后序号，内核只维护全局事件序列，可以让多个读取者独立、非破坏性地读取同一审计流，内核状态也更小。

## 4. P2：用于应对老师深入或开放性问题

### P2-01：当前方案最大的局限是什么？

**建议回答：**

第一，审计是运行期内存日志，不做持久化，重启后记录和序号重新开始；第二，固定环可能覆盖旧事件，
但覆盖可检测；第三，当前同步模型针对单核 rCore，不宣称 SMP 支持；第四，性能只覆盖固定的 pipe
创建/关闭基准，尚未覆盖所有吞吐场景。

### P2-02：攻击者能否通过刷审计事件覆盖重要日志？

**建议回答：**

攻击者可以加速旧记录覆盖，但不能让审计内存无限增长，也不能让覆盖悄悄发生。当前实现用序号、
覆盖计数和 GAP 提示让管理员知道发生了日志缺口。生产级后续可增加速率限制、优先级事件保留、
分级缓冲区和及时导出。

### P2-03：为什么不做持久化审计？

**建议回答：**

项目范围是教学内核中的 IPC 安全机制，优先验证运行期安全闭环。持久化还会引入文件系统一致性、
磁盘配额、崩溃恢复、写放大和权限隔离问题，超出本次课程项目边界。当前设计为后续用户态导出或
持久化扩展保留了稳定 ABI 基础。

### P2-04：如果未来改为 SMP，D 模块最需要修改什么？

**建议回答：**

需要把单核 `UPSafeCell` 替换为适合 SMP 的同步机制，并重新定义锁顺序和内存可见性语义。还需要评估
全局单环在多核下的竞争，可能采用分 CPU 缓冲区加全局序号合并，或更细粒度的无锁/低锁方案。

### P2-05：为什么 D 不记录所有内核事件？

**建议回答：**

审计范围必须可控。v1 重点记录进入安全 IPC 门面的成功、授权/配额/地址失败，以及审计接口自身的
失败；不记录未知 syscall、普通页故障、驱动日志和管道载荷。否则日志量、隐私暴露和性能成本都会失控。

### P2-06：如何证明审计 ABI 未来不会被内部实现变化破坏？

**建议回答：**

内核内部事件和用户态输出结构分离：内部可以调整环形实现，但用户态只看到 `AuditRecordV1` 和
`IpcStatsV1` 的 `#[repr(C)]` 固定布局、版本、大小和稳定操作编号。内部 Rust 枚举顺序或内存布局变化
不会直接暴露到用户态。

### P2-07：`GAP_BEFORE` 为什么只标记批次第一条？

**建议回答：**

缺口发生在“本次读取起点之前”，同一批后续记录已经连续，因此只需给第一条加标记。这样能表达缺口，
又避免重复污染每条记录；而且标记写在输出副本中，不改变内核保存的原始事件。

### P2-08：怎样处理 `u64` 序号溢出？

**建议回答：**

实现使用 `checked_add`。如果下一序号无法表示，就停止接收新的审计事件，不复用旧序号，也不让序号
回绕造成游标语义混乱；更不能改变原 IPC 操作的返回结果。实际课程实验中不可能跑到该上限，但这是
为了保持语义闭合。

### P2-09：这个项目是否能称为完整生产级 IPC 安全方案？

**建议回答：**

不能。它是基于 rCore 第七章的教学内核安全扩展，验证最小凭据、用户内存边界、资源治理和有界审计的
组合设计。它没有覆盖网络 IPC、完整 MAC/SELinux、消息加密、持久化取证、SMP 和完整 POSIX 用户管理。

### P2-10：后续工作优先级是什么？

**建议回答：**

优先方向是：SMP 安全同步；审计速率限制与分级保留；用户态导出或持久化；更全面的管道读写和多核
性能测试；以及更完整的 capability 生命周期管理。这些是在当前可验证安全闭环基础上的自然扩展。

## 5. 容易被问到的“短答版”

| 问题 | 15 秒回答 |
| --- | --- |
| 审计环为什么 256 条？ | 固定容量限制内存上界；当前实现为 256，但工具应通过 `ipc_stat` 查询而不硬编码。 |
| 日志满了怎么办？ | 覆盖最旧记录，不扩内存；用覆盖计数、序号和 GAP 告知读取者数据缺口。 |
| 审计读一次最多多少？ | 最多 32 条，用最后序号分页继续读。 |
| 审计谁能看？ | root 或带 `AUDIT_READ` capability 的进程。 |
| 为什么失败审计调用也要记录？ | 越权、坏参数和坏地址本身是安全行为；成功读不记录以避免自反馈。 |
| 32/32 是什么？ | QEMU 中 28 个预期成功和 4 个预期异常全部按预期结束。 |
| 28/28 是什么？ | 宿主侧审计 ABI、工具和 syscall 边界测试全部通过。 |
| 768/256 是什么？ | 6 个子进程各写 128 个事件，共 768；环最多保留 256，验证有界覆盖。 |
| +15.3% 表示什么？ | 固定 20,000 次 pipe 创建/关闭中，QEMU 端到端中位数从 647 ms 到 746 ms；有常数级开销，无数量级回退。 |
