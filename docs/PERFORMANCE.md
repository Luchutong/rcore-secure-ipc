# IPC 安全路径性能初测

测试日期：2026-09-09（Asia/Shanghai）

## 1. 目的

本轮测量用于提前判断“管道创建接入配额预检查和审计写入”是否出现数量级回退。测试包含未改造的 `main` 基线、D 未接线对照组和当前 C+D 安全路径。它仍不是最终的完整安全版本性能结论：A、B 和 C 的管道读写路径尚未全部集成，最终合并后需要按同一方法重新测量。

## 2. 基准程序

用户程序 `user/src/bin/ipc_bench.rs` 重复执行：

```text
pipe → close(read_fd) → close(write_fd)
```

每个进程先预热 64 次，再执行指定轮数。程序输出总毫秒数、每轮估算纳秒数，以及前后 `ipc_stat` 的审计事件增量。`main` 不包含审计 API，因此临时基准省略计时区间外的两次统计查询，计时区间内的 pipe/close 循环与安全分支一致。计时使用内核已有的毫秒时钟，因此只报告较大样本的中位数，不把微小差异解释为确定开销。

该程序不进入 `usertests`，避免把受宿主机负载影响的耗时阈值变成 CI 偶发失败。常规 CI 仍负责编译它。

运行命令：

```text
ipc_bench 20000
```

每个变体在同一次 QEMU 启动中连续运行 5 个独立进程。环境为 WSL2、单核 rCore、QEMU 8.2.2、release 构建。

## 3. 对比变体

- 原始基线：`main@a74354d`。尚未加入 IPC 安全模块和审计接线。
- D 未接线对照组：`feature/audit-testing`。审计子系统存在，但 `sys_pipe` 尚未接入安全门面，因此每轮不会写管道创建审计事件。
- 安全路径：`audit-c-integration-preview`。`sys_pipe` 经过策略/配额预检查、两端点原子配额申请、完成阶段和审计记录。

原始基线与安全路径给出当前阶段的端到端差异；D 未接线组帮助观察分支体积和 QEMU 调度噪声。最终仍必须以合入 A/B/C/D 后的 `integration` 重新验收。

## 4. 原始结果

| 变体 | 5 次耗时（ms） | 中位数（ms） | 中位每轮（ns） | 每次运行新增审计事件 |
| --- | --- | ---: | ---: | ---: |
| 原始 `main@a74354d` | 685, 657, 647, 647, 645 | 647 | 32,350 | 不适用 |
| D 未接线对照组 | 674, 666, 666, 683, 677 | 674 | 33,700 | 0 |
| C+D 安全路径 | 670, 654, 661, 662, 679 | 662 | 33,100 | 20,000 |

以中位数计算，C+D 安全路径相对原始 `main` 增加 15 ms，即约 `2.3%` 或每轮 750 ns。D 未接线组反而比安全路径慢约 `1.8%`，说明这个量级仍明显受到 QEMU、二进制布局和宿主调度噪声影响。因此当前只能得出“没有出现数量级回退，初测差异约 2.3%”，不能把 2.3% 当作精确开销。安全路径每次都精确新增 20,000 条成功事件，证明测量期间审计接线确实生效，而不是误测未接线代码。

## 5. 复现步骤

分别切换到两个工作树后执行：

```bash
cd os
make run
```

进入用户 shell 后连续执行五次：

```text
ipc_bench 20000
```

保存每行以 `BENCH` 开头的原始输出，按 `elapsed_ms` 排序后取第三项作为中位数。不要混用 debug/release 构建、不同 QEMU 版本或不同迭代次数的数据。

## 6. 最终验收待办

- 在最终 `integration` 上使用同一基准复测，并与本文保存的 `main@a74354d` 数据比较；
- 增加管道读写吞吐量与多进程压力测量；
- 每个变体交替启动并重复多轮，记录宿主环境与原始输出；
- 如需更细粒度结论，改用稳定周期计数或提高单次迭代数，避免毫秒量化误差；
- 最终报告同时给出中位数、离散程度、功能正确性结果和内存上限分析。
